1. Big picture

Stripe Reader M2 is a Bluetooth / USB card reader for in-person payments. Your mobile app does not collect typed card numbers. The reader (or Stripe’s simulator) captures the card; Stripe processes it; your backend authorizes and creates the charge using a secret key that must never live in the app.

Hard rule The Stripe secret key never ships inside a mobile app. Only a trusted server creates connection tokens and payment intents.

2. Stripe sandbox setup

Do all early development in Test mode. Live keys and live readers come later.

Sandbox checklist

1

Switch Dashboard to Test mode

Confirm the Dashboard banner / toggle shows Test (sandbox), not Live.

2

Create a Terminal location

Terminal → Locations → create a location (store / venue). Note the location id — readers connect against a location.

3

Prepare API keys

Create or copy a test secret key for backend / local server use only. Publishable keys alone are not enough for Terminal connection tokens.

4

Choose your reader path

Simulated reader for day-to-day software work, or register a physical M2 to the same location when hardware is available.

5

Verify payments appear

After a successful test collect, confirm the payment shows in the Dashboard under Payments / Terminal activity.

3. Connection setup flow

Connecting a reader is separate from charging a card. Get connection solid first, then run payments.

Reader connection flow

1

Grant device permissions

Location is required by Stripe Terminal. Bluetooth (and related runtime permissions) are required for a physical M2 over Bluetooth.

2

Fetch a connection token from your backend

The app asks your server for a short-lived Terminal connection token. The SDK uses that token to talk to Stripe — the app never invents one.

3

Initialize Stripe Terminal on the device

Start the Terminal SDK once the token provider is wired and the app is ready.

4

Discover readers

Scan for available readers. Use simulated discovery in test mode without hardware, or Bluetooth / USB discovery for a real M2.

5

Select a reader

If more than one appears, staff (or your test UI) chooses which reader to use.

6

Connect to a Terminal location

Connect the chosen reader to your Stripe Terminal location. A connected reader is ready to collect payments.

Healthy connection You should see the reader listed under the location in the Stripe Dashboard (simulated readers update “last seen”; physical readers show when online / recently seen).

4. Simulated vs real Reader M2

Test mode Simulated reader

  • No hardware on the desk
  • Stripe invents a virtual reader for the location
  • Best for CI, day-to-day app work, and demos
  • Still needs backend connection tokens & PaymentIntents
  • Still needs location permission on the device
  • Card presentment is simulated by Stripe

Hardware Physical Reader M2

  • Register the M2 to your Terminal location in Stripe
  • Power on, charge, enable Bluetooth (or use USB)
  • Grant location + Bluetooth permissions
  • Discover with simulated mode off
  • Customer taps, inserts, or swipes a real / test card per Stripe guidance
  • Same app payment APIs as simulated — only discovery / transport differ

Physical M2 first-time setup

1

Register the reader in Stripe

Use Stripe’s register-reader flow so the M2 belongs to your Terminal location.

2

Prepare the tablet

Bluetooth on, location allowed, app built with Terminal enabled for that environment.

3

Discover → Connect

Find the M2, connect it, confirm connected state in the app and Dashboard.

4

Run a small test payment

Prove collect works on hardware before wiring it into your full POS journey.

5. End-to-end payment flow

Once a reader is connected, payment is a handoff between your app, your backend, Stripe, and the reader.

Staff
Starts “Collect payment” for an amount (or an order / bill). App already has a connected reader (or connects first).
App
Requests a card-present PaymentIntent from your backend. Sends amount / currency / order reference as your contract defines.
Backend
Creates a Stripe PaymentIntent with card-present methods using the secret key. Returns payment id + client secret to the app. Never returns the secret API key.
App + SDK
Hands the client secret to Stripe Terminal to collect and confirm on the reader. No PAN / CVV is typed into your UI for this path.
Reader
Customer presents the card (or simulator completes in test mode). Card data stays in Stripe’s reader / payment stack.
Stripe
Authorizes / captures per your PaymentIntent settings. Optionally notifies your backend via webhooks.
App
Receives succeeded, declined, or canceled. Update UI; treat webhook + server state as source of truth when available.
Outcome What it means Typical next step
Succeeded Card present payment completed Mark order paid; print / receipt flows
Declined Issuer or Stripe refused the charge Show clear message; allow retry or other tender
Canceled Staff or system aborted collect Return to amount / tender selection

6. What we need from backend teams

Mobile can discover and drive the reader. Backend owns trust, money creation, and durable order state.

01

Connection token endpoint

Authenticated API that creates a Stripe Terminal connection token and returns only the token secret to the app. Called often; must be fast and locked to authorized devices / users.

02

Create card-present PaymentIntent

Authenticated API that creates a PaymentIntent suitable for in-person collection and returns id + client secret. Prefer deriving amount from a known order / bill when your domain has one.

03

Auth & tenancy

Only signed-in or paired devices for a given merchant / store may create tokens and charges. Map store → Stripe Terminal location server-side.

04

Idempotency

Retries from flaky networks must not create duplicate charges. Use Stripe idempotency keys keyed to the business operation.

05

Webhooks

Listen for payment succeeded / failed (and related events) so order paid state survives app crashes after collect.

06

Post-payment operations

Refunds, tip adjustment, capture strategy (automatic vs manual) — owned by backend and product policy, not ad-hoc in the client.

07

Secrets & environments

Test vs live Stripe keys per environment in a secrets manager. Never expose secret keys to mobile config files.

Out of scope for backend Bluetooth discovery, USB pairing UX, and prompting the customer on the reader stay on the mobile Stripe Terminal SDK.

7. Go-live readiness

Phase A — Sandbox software ready

Test location exists Terminal location created; app/backend agree on which location to use.
Backend token + PaymentIntent APIs work in test App can initialize Terminal and create charges without embedding secrets.
Simulated discover → connect → pay succeeds Full path proven without hardware.
Dashboard shows test payments Ops can reconcile a successful collect in Stripe.

Phase B — Hardware ready

M2 registered to the correct location Reader appears under the intended Terminal location.
Permissions UX verified on target tablets Location + Bluetooth prompts are clear; denial paths are handled.
Physical discover → connect → pay succeeds At least one pilot device + one M2 pair validated on-site Wi‑Fi / RF conditions.

Phase C — Production ready

Live Stripe account & live keys locked down Secrets only on servers; key rotation playbook exists.
Auth, tenancy, idempotency, webhooks shipped Order paid state is trustworthy under retries and offline blips.
Refund / tip / capture policy implemented Support and ops know how to reverse or adjust a payment.
Monitoring & support runbook Failed connects, declines, and webhook gaps have owners and playbooks.
Pilot store sign-off One real location completes training and a supervised live transaction.
